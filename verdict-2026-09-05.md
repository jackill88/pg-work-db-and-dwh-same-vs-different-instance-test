# Benchmark verdict — 2026-09-05

## Conclusion

**DWH on the same PostgreSQL instance as a live OLTP database is not a great idea.**

The fresh runs at a sustained **~1,750 ops/s** (100% success rate, 0 errors) provide clean evidence. Earlier runs at the same target were invalid due to loadgen bugs (~60% failures) and are excluded from this verdict.

---

## Test setup

| Parameter | Value |
|---|---|
| Live target load | 1,750 ops/s (mixed read/write) |
| Duration | ~5 minutes per scenario |
| Live workers / pool | 32 / 48 connections |
| DWH load | 5k-row bulk inserts every 2s + 15 analytical readers |
| Hardware | Ryzen 5 2600X, 16 GB RAM, NVMe |


---

## Load generator health

Both scenarios sustained the target load without client-side errors.

| Metric | Same instance | Separate instances |
|---:|---:|---:|
| Target | 1,750 ops/s | 1,750 ops/s |
| Achieved | **1,704 ops/s** (97%) | **1,720 ops/s** (98%) |
| Success rate | **100%** | **100%** |
| Errors | 0 | 0 |

---

## Live OLTP

Separate instances deliver modest but consistent improvements. Colocation does not reduce throughput at this load level.

| Metric | Same instance | Separate instances | Change |
|---:|---:|---:|---|
| Mean latency | 6.37 ms | 5.50 ms | **−14%** |
| p95 reads | 8 ms | 8 ms | ~same |
| p95 writes | 32 ms | 16 ms | **−50%** |
| Throughput | 1,704 ops/s | 1,720 ops/s | +1% |
| Active PG connections (avg) | 23.8 | 20.1 | −16% |

| Operation | Same instance | Separate instances |
|---:|---:|---:|
| Point read | 3.64 ms | 3.12 ms |
| Recent-order scan | 3.75 ms | 3.21 ms |
| Insert order | 12.68 ms | 11.03 ms |
| Update balance | 12.54 ms | 10.92 ms |

**Assessment:** Live OLTP remains usable on a shared instance at 1,750 ops/s, but write tail latency doubles. Separation buys predictability, not raw RPS.

---

## DWH analytics

This is where colocation hurts most.

| Metric | Same instance | Separate instances | Change |
|---:|---:|---:|---|
| Analytical read (mean) | **1,755 ms** | **450 ms** | **−74%** |
| Analytical read (p95) | **~4,176 ms** | **~850 ms** | **−80%** |
| Bulk insert (mean) | 376 ms | 267 ms | −29% |
| Bulk insert (p95) | ~837 ms | ~411 ms | −51% |
| DWH ops completed (5 min) | **2,348** | **6,160** | **+162%** |

**Assessment:** A shared PostgreSQL process completed **2.6× less DWH work** in the same window, with analytical queries **~4× slower**. Bulk loads also regress, but the analytical read penalty is the dominant story.

---

## Summary by concern

| Area | Same-instance impact | Severity |
|---|---|---|
| DWH analytics | ~4× slower reads, far fewer completed queries | **High** |
| Live write tail latency | p95 writes 2× worse | **Medium** |
| Live mean latency | ~14% slower | **Low–medium** |
| Live throughput | No meaningful difference | **Neutral** |
| Buffer cache | 99.99–100% hit ratio in both runs | Not the bottleneck |

The performance gap is driven by **cross-workload contention** (CPU, I/O, locks), not insufficient shared buffers.

---

## Cloud and network caveat

On cloud infrastructure, separate instances may look more attractive on paper — dedicated CPU and memory per role — but **network latency becomes a new variable**:

- Usually irrelevant for this benchmark (direct DB connectivity, no cross-DB queries).
- Matters when the live app must query the DWH (or vice versa) over the network.
- For bulk ETL/replication between live and DWH, network bandwidth and latency should be modeled explicitly in the next phase.

Separation trades **on-host contention** for **cross-network hops**. The right choice depends on whether workloads are truly isolated or frequently join across the boundary.

---

## One-liner

> Under a sustained 1,750 ops/s mixed OLTP load, colocating DWH on the same PostgreSQL instance increased live write p95 latency by 2× and DWH analytical query latency by 4×, while reducing completed DWH work by 62% — with no meaningful gain in live throughput.

---

## Recommendation

1. **Do not colocate DWH and live OLTP** on one PostgreSQL instance when analytical workloads run concurrently with production traffic.
2. **Separate instances** (or equivalent isolated compute) for the DWH tier; keep live OLTP on its own server.
3. **Re-run 2–3 times** per scenario for confidence intervals before publishing externally.
4. **Next phase:** Add an API gateway in front of live DB to model a realistic application path; evaluate any live↔DWH cross-queries over the network explicitly.
